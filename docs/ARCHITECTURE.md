# Architecture

Godot 4.3 project targeting the **Mobile** renderer. All gameplay code is typed GDScript.

## Guiding rules

- **The model is kept separate from presentation.** The player's state (`PlayerProfile` and the classes it composes) and combat rules (`BattleState`) are plain `RefCounted` classes. They hold no nodes and have no rendering. They take content lookups as callables, use seeded random numbers, and report what happened as plain dictionaries. A future server could run them unchanged.
- **Systems talk through signals.** Systems that produce facts emit them on `EventBus` (for example `item_collected`, `npc_talked` or `encounter_won`). Consumers react to those signals: `Game` routes them into the quest log, and the HUD and audio respond on their own.
- **Content is data.** `.tres` resources (items, spells, creatures, encounters, quests, status effects, biomes) are generated by `tools/build_content.gd`. Dialogue, the skill tree and shops are JSON files in `resources/`.
- **Few singletons, each justified.** The autoloads are:
  - `EventBus`: signals only
  - `Settings`: persisted options
  - `Database`: read-only content registry
  - `Game`: owns the session profile and routes events
  - `SaveManager`
  - `AudioManager`
  - `SceneFlow`: scene and region transitions

## Scene flow

`main_menu.tscn` → `SceneFlow.start_new_game()` or `continue_game()` → `game.tscn` (`GameRoot`).

`GameRoot` does the following, in this order:

1. Builds the UI layer: HUD, touch controls, dialogue box, Grimoire, shop, pause menu and loading screen.
2. Instantiates the region scene listed in `Database.REGIONS` and awaits `Region.build()`, which reports progress to the loading screen.
3. Spawns `player.tscn` at the pending spawn: a named spawn point, or the position stored in the save.
4. Coordinates modal UI states (`lore`, `dialogue`, `grimoire`, `shop`, `pause`, `combat`) to turn player control, touch controls and mouse capture on and off.

Combat does not change scenes. `CombatManager` builds a `CombatArena` at y = 800 with its own camera and environment, then hides the region. The exploration state stays in memory, so returning to it is instant.

## World generation

| Piece | Responsibility |
|---|---|
| `MeshKit` | Indexed mesh builder: rings, tubes along paths, lathe, ellipsoids, crystal prisms; smooth normals. Godot front faces are clockwise and the helpers follow that convention. |
| `MushroomGenerator` + `MushroomParams` | 7 cap shapes, bent/twisted stems, asymmetry, lobes, glowing rim and gills, spots, tendrils, LOD `detail`; outputs a convex cap hull for walkable collision. |
| `TreeGenerator`, `CrystalGenerator`, `IslandGenerator`, `FlowerGenerator` | Further procedural assets. Flowers are animated rigs that switch to a merged far LOD mesh. |
| `DreamTerrain` | An analytic height function built from noise, a surrounding rim, hills, flattened plazas, basins and sunken paths. Produces a 5×5 grid of render chunks plus a `HeightMapShape3D`. Generators query it through `height_at()`, `normal_at()` and `path_distance()`. |
| `Scatter` | Placement with spacing, slope limits, height bands, exclusion circles, path margins, density maps and count caps. |
| `SpatialBatcher` | Static batching per grid cell and material, used for trees and crystals. |
| `Region` | Base class: atmosphere (`make_environment`), sun, spawn points, reaction to graphics presets (`register_detail`). |
| `DreamingMeadow` + `MeadowLandmarks` | The first region's layout, landmarks, interactables, NPCs, creatures and quest-driven changes to the world. |

Materials come from `MaterialLib`, which caches them. Every opaque surface uses `shaders/organic.gdshader`:

- the vertex color is the albedo
- the vertex **alpha is an emission mask**
- lighting is a soft banded toon light() with a rim

## Gameplay systems

| System | Files |
|---|---|
| Interaction | `Interactable` (Area3D on layer 3) and its subclasses `Collectible`, `LoreObject`, `Mechanism`, `RegionPortal`, `RestPool`, `NPC.NPCInteract`. The player first casts a ray from the camera, then falls back to a forgiving proximity cone (for touch). |
| Dialogue | `DialogueRunner` walks JSON trees. `DialogueLogic` holds the shared condition and action vocabulary (`objective_current:…`, `give_item:…`, `start_quest:…`, …). |
| Quests | `QuestLog.handle_event(type, target)`. Objectives can be sequential or not, collect objectives sync with the inventory, and prerequisites and auto-start chain quests together. Rewards are granted through `PlayerProfile.grant_rewards`. |
| Progression | `PlayerStats` (levels, growth and bonuses), `SkillTreeState` (JSON trees), `Spellbook` (known spells and deck rules). |
| Inventory | `Inventory`: slots, stack limits, equipment, currency. |
| Combat | `BattleState` (rules), `EnemyAI` (utility scoring), `CombatManager` (finite state machine), `CombatArena` (presentation), `SpellVFX`, `CombatHUD` + `SpellCardView`. |
| Saving | `SaveManager` (slots, atomic write plus `.bak`, autosave), `SaveSchema` (version 3 with migrations 1→2→3, sanitizing). |
| Audio | `AudioManager`: buses Master, Music, Ambient, Effects and UI; a voice pool; music crossfades; ambience. |

### Combat state machine

`INITIALIZING → INTRO → TURN_START → PLAYER_TURN → CARD_SELECTION ⇄ TARGET_SELECTION → SPELL_RESOLUTION → STATUS_EFFECT_RESOLUTION → ENEMY_TURN → TURN_START …`

The battle ends in `VICTORY` or `DEFEAT`, then `EXITING`. The machine only advances on explicit transitions, player-action signals from the HUD, or awaited presentation. The one exception is a short presentational pause between floating numbers, which never decides an outcome.

## Multiplayer readiness (not implemented)

- Game logic does not depend on the network. A battle starts from a *snapshot* of the player, its random numbers are seeded, and it outputs event lists that a client could replay. A test checks that the same seed produces the same battle.
- The economy and rewards are computed in the model (`grant_rewards`, `compute_rewards`). A server would own these, and a client would only display the results.
- `PlayerProfile.player_id` exists so player identity can be added later.

## Testing

`tests/test_runner.tscn` runs every `tests/test_*.gd` (`TestCase`). It has 51 tests:

- unit tests for each model
- player physics tests on a real `CharacterBody3D` with simulated input
- full `CombatManager` runs driven by an automated player

Use `--fixed-fps 60` so tweens advance by frame count rather than wall-clock time.
